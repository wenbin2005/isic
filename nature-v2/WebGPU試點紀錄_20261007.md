# 自然漫遊 v2：森林 WebGPU 試點紀錄（2026-10-07）

基準版本：`main`（PR #1 四景美化已合併）。需求：用 webgpu-render-pipeline 技能美化四景；使用者選定「森林試點」——只有森林改走 WebGPU + TSL，加上 TAA 與天空大氣，另外三景維持 WebGL，並保留 WebGL 備援。

## 範圍

- [事實] 只有森林（`GPU_SCENES = new Set(['forest'])`，`engine.js`）走 WebGPU；海岸、秋林、雪林的程式路徑與 PR #1 相同。
- [事實] 行走、碰撞、邊界與地面高度演算法（`pathX`…`terrainHeight`、`allowed`、`move`）沒有改動。
- [事實] three.js 版本維持 r186；新增 `vendor/three.webgpu.js`、`vendor/three.tsl.js` 與 `vendor/addons/tsl/`（TRAANode、TAAUtils），授權同 `vendor/THREE-LICENSE.txt`（MIT）。

## 引擎選擇與備援

| 情況 | 結果 |
|---|---|
| 瀏覽器有 `navigator.gpu` 且取得 adapter，進入森林 | WebGPU 版森林 |
| 網址加 `?gpu=0` | 強制 WebGL（與 PR #1 相同畫面） |
| WebGPU 初始化失敗 | 換一張新 canvas，退回 WebGL，並記住本次不再嘗試 |
| 森林 ↔ 其他三景互切 | 引擎不同時釋放舊 explorer、換新 canvas 重建 |

## 改了什麼

| 類別 | 內容 | 位置 |
|---|---|---|
| 天空大氣 | Hillaire 2020 參數的單次散射光線步進（視線 32 步 × 光線 8 步），每景烘一次 256×128 半精度 LUT（仰角平方根映射）；另加偏藍的多次散射近似與大氣層外白色日光 | `gpu.js` `createGpuAtmosphere` |
| 雲、日輪、環境光 | 背景節點畫雲與日輪；同一片天空穹頂經 PMREM 烘出環境光 | `gpu.js` `installSky` |
| 霧 | 與 WebGL 版同一條高度霧公式，但在線性空間計算；霧色取自天空 LUT，朝太陽方向加前向散射 | `gpu.js` `fogNode` |
| TAA | `pass()` + MRT（output、velocity）接 three 內建 `traa()`；渲染器關閉 MSAA | `gpu.js` `createPipeline` |
| 風吹 velocity | 葉片風擺的頂點位移同時寫入 `positionPrevious`（用上一幀時間），TAA 才不會把擺動當成鬼影 | `gpu.js` `patchFoliage` |
| 材質 | 葉片、樹皮、岩石、地面改成 node 材質並移植原 GLSL 效果；溪水、光束、浮塵改寫為 TSL | `gpu.js` `patch*`、`creekMaterial`、`shaftMaterial`、`moteSprites` |
| 浮塵 | WebGPU 的點固定 1 像素，改用實例化 Sprite | `gpu.js` `moteSprites` |

## 手調值（無實測依據，依截圖目視調整）

| 參數 | 值 | 理由 |
|---|---|---|
| `skyGain` | 2 | 天頂原本偏灰暗；調後天頂約 `#3363a3`、地平線約 `#d8e5eb`（numpy 模型試算） |
| `fogGain` | 0.7 | 霧原本過白過濃 |
| `FOG_DENSITY` | 0.65 | 同上 |
| `DISPLAY_TO_HDR` | 2 | 光束與浮塵原本在顯示空間相加，換到線性 HDR 後需放大才看得到 |

## 踩過的雷

1. [事實] Chrome 141 不認 three r186 建立貼圖視圖時帶的 `swizzle:'rgba'`，會拋 TypeError。`gpu.js` 的 `tolerateIdentitySwizzle()` 在第一次失敗後改為移除這個恆等欄位重試。
2. [事實] `vec3(new THREE.Color(x))` 在 TSL 得到接近 0 的值，光束與溪水因此消失、變暗；改用 `rgb()` 取出 r、g、b 三個分量。
3. [事實] 解析 GLSL 字串 `vec3(...)` 時正規式把 `vec3` 的 3 也當成數字，造成紅橘拖影與粉紅遠山；先移除前綴再解析。
4. [事實] 所有 `THREE.Sprite` 共用同一個模組層級幾何體。切換畫質重建場景時 `disposeGroup` 把它釋放，新建的浮塵 Sprite 便送出已銷毀的緩衝區（`[Buffer] used in submit while destroyed`）。改為讓浮塵 Sprite 使用自己的幾何體副本。用二分法逐一跳過釋放步驟找到：跳過 `disposeGroup` 錯誤消失，只跳過暫存貼圖或環境貼圖仍會出錯。
5. [事實] WebGPU 的陰影節點自行持有陰影圖並依 `mapSize` 調整，外部不可釋放（`applyLook` 只在 WebGL 釋放）。

## 驗證（雲端容器，Chromium 141 + SwiftShader 軟體 WebGPU，約 0.2 FPS）

- [事實] 森林以 `webgpu` 後端啟動，無錯誤；畫面有遠山、光束、天空與霧。
- [事實] 切景 森林(webgpu) → 海岸(webgl) → 秋林(webgl) → 森林(webgpu)，每次都 ready，頁面始終只有一張 canvas。
- [事實] 森林切換到「流暢」畫質後無 GPU 驗證錯誤。
- [事實] `?gpu=0` 走 WebGL，與 PR #1 相同。
- [事實] repo 內 `驗證.cjs` 依賴 `dist/` 建置產物與 Windows 路徑，雲端無法執行，本次未跑。

## 限制與未驗證

- [事實] 實機效能（實體顯卡、手機）完全未量測；軟體 WebGPU 的速度沒有參考價值。
- [事實] TAA velocity 的正確性只有目視，沒有數值量測。
- [推論] 天空 LUT 每景只烘一次，太陽不動時成本只在開機；若日後要讓太陽移動，需改成每幀或按需重烘。
- [推論] 新舊截圖不是同一次執行、同解析度，新版截圖帶暫停介面，只能比較整體觀感，不能逐像素比對。
- [建議] 合併前請在有實體顯卡的 Chrome / Edge 開森林，觀察幀率與 TAA 是否有拖影；若有疑慮，加 `?gpu=0` 對照。
